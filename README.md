# 塑忆 · Shaping Memory

> shape of my memory, snapshot of my mind
> 塑记忆之形，撷心影之瞬

> This project is 99% generated by AI agents.

塑忆是一个自托管的个人影像平台：把散落在硬盘里的照片整理成可浏览、可检索、可授权分享的影像档案。
包含 Web 前台、Web 后台、移动端与后端 API 四个可独立运行的应用，共用一套领域模型与 API 客户端。

## 核心功能

### 影像浏览（Web 前台 / 移动端）

- **两种浏览形态**：瀑布流「图墙」与紧凑「列表」，同一份数据两种读法。
- **时间线导航**：按年月生成进度轨，滚动时高亮当前位置并可反向定位；
  图墙按列插入跨月分割线，列表按年月分组，两者与照片日期严格对齐。
- **照片查看器**：键盘 / 滚轮切换、EXIF 侧栏卡片、底部胶片条、原片按需加载。
- **相册与分类**：动态相册（可自定义封面与排序）与分类筛选，均可后台增删改。
- **实况照片**：识别 Motion Photo，卡片带角标，查看器内可播放其内嵌视频。

### 后台管理（Web 后台）

| 模块 | 能力 |
| --- | --- |
| 数据概览 | 照片 / 软删除 / 实况 / 受保护计数、相册分类账号数、有效分享数、最新拍摄日 |
| 照片管理 | 15 列信息（含曝光三要素与坐标）、6 维组合检索、批量改元数据、批量改 EXIF（含地图选点）、批量上传（拖拽 + 格式与体积校验） |
| 相册管理 | 相册增删改、成员与排序、封面设置、公开 / 私有 |
| 分类管理 | 分类增删改与排序（改名时同事务同步照片的分类字段） |
| 账号管理 | 创建账号、分配角色、重置密码 |
| 隐私与分享 | 全局隐私策略、全局查看密码、分享链接全生命周期管理 |
| 系统设置 | 站点标题 / 标语、上传上限与允许格式、默认分类 |
| 操作日志 | 所有写操作的审计流水（含失败尝试） |

### 照片隐私与授权

- **四级隐私标记**（单张覆盖全局默认）：`inherit` 跟随全局 / `visible` 强制公开 / `blur` 模糊展示 / `hidden` 完全不出现。
- **模糊不泄露原图**：模糊版由服务端预生成，图片地址全部由后端拼装下发，
  前端**拿不到也拼不出**原片地址，不存在「前端拼错地址导致泄露」的路径。
- **模糊算法（五段式，隐私与观感分离）**：
  `降采样到 8px → 放大回 640px → 展示尺寸下真高斯模糊 → 噪点抖动 → 低质量 JPEG`。
  安全边界是**降采样底线**而不是高斯半径 —— 实测定标：底线 32px 时满幅人像的眉毛、
  双眼、鼻、嘴仍清晰可辨，24px 五官清晰，16px 明显可辨，12px 已能看出眼窝，
  只有 **≤8px** 才彻底读不出五官；而高斯 σ 再大也压不住（五官在放大后的尺度上
  属于低频结构，σ35 叠在 10px 上仍透出结构）。因此底线是**代码常量、不可配置**，
  免得有人把它调回 32px 而界面仍显示「已保护」。后台的模糊强度滑杆只调
  高斯 σ / 噪点 / 压缩质量，**只影响观感，任何档位都安全**。
  规格参数（降采样底线 / σ / 噪点 / 编码质量 / 输出尺寸）由后端随策略下发，
  后台「隐私与分享」页实时展示当前档位真正生效的值。
- **三种授权查看方式**：
  1. **授权账号**：登录具备权限的账号后可见；
  2. **独立密码**：可为单张照片设置独立查看密码（与全局密码并存）；
  3. **时效链接 + 提取码双重校验**：生成带有效期的分享链接，链接被转发出去后仍需 4~6 位提取码；
     撤销后立即失效，记录保留便于追溯。

### 后端 API

NestJS 模块化单体，统一前缀无、按资源分组：`/auth`、`/photos`、`/files`、`/albums`、`/categories`、
`/settings`、`/privacy`、`/share`、`/users`、`/stats`、`/audit`、`/health`。
认证用 JWT，权限按 `admin / editor / viewer` 三级角色判定。

## 技术栈与目录结构

**技术栈**：TypeScript + NestJS + Drizzle ORM + PostgreSQL / React 18 + Vite / React Native（Expo）/ npm workspaces 单仓多包。

```
shaping-memory/
├── apps/
│   ├── api/               后端 API（NestJS）
│   ├── web/               前台（React + Vite，hash 路由）
│   ├── admin/             后台（React + Vite + Ant Design）
│   └── mobile/            移动端（Expo / React Native）
├── packages/
│   ├── core/              领域模型与纯函数（类型、时间线、EXIF 字段表、地理计算）—— 三端共用
│   ├── sdk/               统一 API 客户端 —— 三端共用
│   ├── db/                Drizzle 表定义、客户端与迁移记录（drizzle/）
│   ├── config/            环境变量校验（zod）
│   ├── exif/              exiftool 封装（抽取 / 写回 / 实况视频提取）
│   ├── image/             Sharp 图像处理（缩略图、模糊图）
│   ├── storage/           存储适配层（本地文件系统 / S3 兼容对象存储）
│   └── design-tokens/     设计 Token 与主题 CSS（唯一色彩字体来源）
├── CONTRIBUTING.md        贡献指南（环境搭建、分支与提交规范、PR 流程）
├── LICENSE                AGPL-3.0 许可全文
├── docs/                  产品设计方案、设计语言 Token 规范、动效规范
├── sql/                   数据库表结构脚本（换环境从零重建用）
├── prototypes/            UI 原型（静态 HTML，仅供设计参考）
├── tools/                 第三方工具根目录（每个工具一个子目录，二进制不入库）
└── data/                  运行时生成物（缩略图、模糊图、实况视频、EXIF 备份，不入库）
```

**前端与后端的关系**：Web 与移动端都只通过 `packages/sdk` 访问 API，
不直接读数据库、不拼图片地址；后端返回相对路径，由 sdk 统一补成绝对地址。

### 安装 ExifTool

`tools/exiftool/` 下的 exiftool 发行版（约 33 MB）**不入库**，需要手工放置：

1. 打开 <https://exiftool.org/>，下载 **Windows Executable**（Oliver Betz 打包版，13.x）；
2. 解压后把 `exiftool.exe` 与 `exiftool_files/` 一起放到本仓库的 `tools/exiftool/` 目录。

> ⚠️ 该打包版按「当前工作目录」定位 `exiftool_files` 与 `perl532.dll`，
> 因此调用方必须把工作目录设在该可执行文件所在目录（`packages/exif` 已处理），
> 直接用绝对路径调用会报 `code 126`。

## 快速开始

```bash
# 1. 取代码
git clone <仓库地址> && cd shaping-memory

# 2. 装依赖（在仓库根执行一次即可，workspaces 会装齐所有包）
npm install

# 3. 配置环境变量
cp .env.example .env
#    编辑 .env：填 DATABASE_URL、JWT_SECRET、ADMIN_PASSWORD，
#    并把 PHOTO_SOURCE_DIR 指向你的原片目录

# 4. 建表 + 写入初始数据
npm run db:push          # 按 packages/db/src/schema.ts 同步表结构
npm run db:seed          # 角色 / 权限 / 初始管理员
npm run db:seed:catalog  # 分类与相册初始数据（可选）

# 5. 导入照片（扫描 PHOTO_SOURCE_DIR）
npm run import:photos

# 6. 起服务（建议开三个终端）
npm run dev:api     # → http://127.0.0.1:3000
npm run dev:web     # → http://localhost:5173   前台
npm run dev:admin   # → http://localhost:5174   后台
```

数据库在远程服务器时，把 `DATABASE_URL` 直接指向远程地址即可，不需要 SSH 隧道：

```bash
# 远程库只绑了 127.0.0.1:5432，可在服务器上用 nginx 的 stream 模块转发出一个对外端口
# .env 里直接写远程地址
DATABASE_URL=postgresql://USER:PASSWORD@<REMOTE_HOST>:15432/shaping_memory
```

后台登录用 `.env` 里的 `ADMIN_USERNAME` / `ADMIN_PASSWORD`
（`db:seed` 只写入一次，之后改密在后台「账号管理」里做）。

## 配置项说明

全部配置集中在仓库根 `.env`（模板见 `.env.example`），由 `packages/config` 用 zod 校验，
缺失或不合规会在启动时立刻报错，不会带着半截配置跑起来。

| 变量 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- |
| `DATABASE_URL` | ✅ | — | PostgreSQL 连接串 |
| `PHOTO_SOURCE_DIR` | ✅ | — | 原片来源目录（只读，导入脚本扫描它） |
| `STORAGE_DIR` | ✅ | — | 生成物目录（缩略图 / 模糊图 / 实况视频 / EXIF 备份） |
| `TOOLS_DIR` | ✅ | — | 第三方工具根目录；Windows 打包版需含 `exiftool/exiftool.exe`，Linux 系统包直接填 `/usr/bin` |
| `JWT_SECRET` | ✅ | — | 会话签名密钥，≥ 16 位随机字符 |
| `ADMIN_PASSWORD` | ✅ | — | 初始管理员口令，≥ 8 位（仅 seed 使用） |
| `ADMIN_USERNAME` | | `admin` | 初始管理员账号 |
| `API_PORT` / `API_HOST` | | `3000` / `127.0.0.1` | API 监听地址 |
| `PUBLIC_BASE_URL` | | `http://127.0.0.1:3000` | API 对外基址（拼 og:image 等绝对地址） |
| `WEB_BASE_URL` | | `http://localhost:5173` | 前台地址（分享链接落地页） |
| `CORS_ORIGINS` | | 空 | 允许跨域的前端来源，逗号分隔；**留空 = 放行所有，仅限本地开发** |

**三个目录变量支持相对路径**，相对的是仓库根目录，例如 `STORAGE_DIR=./data`
（换机器、换盘符都不用改）；写绝对路径则原样使用。

**前端 API 地址是构建期变量**，Vite 与 Expo 只读各自 app 目录下的 `.env`，因此打包时用行内变量注入：

```bash
VITE_API_BASE=https://api.example.com npm run build:web
EXPO_PUBLIC_API_BASE=https://api.example.com npx expo prebuild --platform android
```

## 部署到服务器

以「一台 Linux 服务器 + nginx + 单域名子路径 + HTTPS」为例（本项目线上即为该形态）。
证书是**只绑定 `<YOUR_DOMAIN>` 的单域名证书**，因此三端全部挂在这一个域名的不同子路径下：

| 用途 | 地址 | 后端 |
| --- | --- | --- |
| 前台 | `https://<YOUR_DOMAIN>/shaping-memory/` | 静态文件（`apps/web/dist`） |
| 后台 | `https://<YOUR_DOMAIN>/shaping-memory/admin/` | 静态文件（`apps/admin/dist`） |
| API | `https://<YOUR_DOMAIN>/shaping-memory/api/` | Node 进程（`apps/api`） |

> - 三端同域同证书，浏览器侧就是同源，`CORS_ORIGINS` 只需填 `https://<YOUR_DOMAIN>`。
> - 资源前缀由 `apps/web/vite.config.ts` / `apps/admin/vite.config.ts` 的 `base` 决定，
>   **改路径必须同步改 base 并重新打包**，否则页面会去根路径找 `assets/*` 而 404。

### 1. 准备运行时

```bash
# Node.js（以 22.x 为例，按需换版本）
cd /opt && curl -fsSLO https://nodejs.org/dist/v22.14.0/node-v22.14.0-linux-x64.tar.xz
tar -xf node-v22.14.0-linux-x64.tar.xz && mv node-v22.14.0-linux-x64 node
ln -sf /opt/node/bin/node /usr/local/bin/node
ln -sf /opt/node/bin/npm  /usr/local/bin/npm

# ExifTool（Linux 用系统包即可，无需 tools/ 目录）
dnf install -y perl-Image-ExifTool
```

### 2. 放置代码与配置

```bash
mkdir -p /opt/shaping-memory && cd /opt/shaping-memory
git clone <仓库地址> .

# 生产 .env：DATABASE_URL 指向本机库，TOOLS_DIR 指向系统 exiftool 所在目录
cp .env.example .env && vi .env
```

生产 `.env` 与开发的三点差异：

```ini
API_HOST=127.0.0.1                    # 只监听本机，由 nginx 反代，不直接暴露
CORS_ORIGINS=https://<YOUR_DOMAIN>     # 三端同域，只需放行这一个源
PUBLIC_BASE_URL=https://<YOUR_DOMAIN>/shaping-memory/api
WEB_BASE_URL=https://<YOUR_DOMAIN>/shaping-memory
TOOLS_DIR=/usr/bin
```

### 3. 建库与初始数据

生产库建议**独立于开发库**，且用**独立账号** —— 否则线上和本地写回的照片绝对路径会互相覆盖。

```bash
psql -h 127.0.0.1 -U postgres -f sql/00_bootstrap.sql   # 建库 + 应用账号
psql -h 127.0.0.1 -U postgres -c "CREATE DATABASE shaping_memory_prod OWNER shaping;"

# 账号口令不要经过任何传输通道，在服务器上现场生成再写进 .env（这条只用一次）：
psql -h 127.0.0.1 -U postgres -c "ALTER ROLE shaping WITH PASSWORD '$(openssl rand -hex 24)';"
# ↑ 如果这样会看不到口令，就直接设置成你知道的值，或改用脚本写入 .env

# 建表（三选一）：跑迁移、从 sql/ 脚本重建，或由 Drizzle 按 schema.ts 同步
npm ci && npm run db:migrate
# 或者：for f in sql/0[1-7]_*.sql; do psql -h 127.0.0.1 -U shaping -d shaping_memory_prod -f "$f"; done
# 或者：npm ci && npm run db:push

# 初始数据
npm ci && npm run db:seed && npm run db:seed:catalog
```

### 4. 安置照片文件（关键：数据库存的是绝对路径）

**这一节的问题必须了解**：`media.source_path` / `thumb_path` / `live_video_path` 三列存的是
**导入时那台机器上的绝对路径**，直接换台机器跑就全 404。因此照片文件有两种上法：

- **方式 A（推荐，省流量）**：本机生成一套「展示档」预览图（长边 1920、保留 EXIF），
  连同 `data/thumbs`、`data/live` 一起上传到服务器的 `photos/` 与 `data/`，
  然后把库里三列路径按前缀改写：

  ```sql
  -- 前缀替换成服务器路径，再把 Windows 反斜杠统一成正斜杠（Linux 不认反斜杠）
  UPDATE media SET
    source_path     = replace(replace(source_path,     'D:\原片目录', '/opt/shaping-memory/photos'), E'\\', '/'),
    thumb_path      = replace(replace(thumb_path,      'D:\本地\data', '/opt/shaping-memory/data'),  E'\\', '/'),
    live_video_path = replace(replace(live_video_path, 'D:\本地\data', '/opt/shaping-memory/data'),  E'\\', '/');
  ```

  > 生成预览档时必须保留 EXIF（sharp 默认会剥掉），否则后台的「EXIF 全量编辑」读不到机身镜头。

- **方式 B（最忠实）**：把原片一起上传到服务器，在服务器上跑一次
  `PHOTO_SOURCE_DIR=/opt/shaping-memory/photos npm run import:photos`，
  路径由导入管线直接写成正确值 —— 代价是要上传全部原片。

### 5. 构建前端并放置静态文件

本项目前台与 API **同源**（都在 `<YOUR_DOMAIN>` 下），所以 `VITE_API_BASE` 直接用根相对路径即可 ——
产物不绑定协议，HTTP 与 HTTPS 下都能跑，换域名也不用重新打包：

```bash
VITE_API_BASE=/shaping-memory/api npm run build:web
VITE_API_BASE=/shaping-memory/api npm run build:admin

mkdir -p /var/www/shaping-memory-web /var/www/shaping-memory-admin
cp -r apps/web/dist/.   /var/www/shaping-memory-web/
cp -r apps/admin/dist/. /var/www/shaping-memory-admin/
```

> 若前后端确实要分开部署（不同源），再改成 `VITE_API_BASE=https://api.example.com` 这种绝对地址。

### 6. 配置 nginx（HTTPS + 子路径）

证书是单域名的，先摆到位（`pem` 是「站点证书 + 中间证书」的串接体；`.key` 权限收到 600）：

```bash
install -d -m 700 /etc/nginx/ssl
install -m 600 <YOUR_DOMAIN>.pem /etc/nginx/ssl/<YOUR_DOMAIN>.pem
install -m 600 <YOUR_DOMAIN>.key /etc/nginx/ssl/<YOUR_DOMAIN>.key
```

`/etc/nginx/conf.d/shaping-memory.conf`（旧的 `shaping-memory-{web,admin,api}.conf`
三个子域名文件在此形态下已不需要，删除即可）：

```nginx
# 80 端口只做跳转，不再承载页面
server {
    listen 80;
    server_name <YOUR_DOMAIN>;
    return 301 https://$host$request_uri;
}

server {
    # nginx 1.24 用这种写法开 HTTP/2；1.25.1+ 可换成独立的 `http2 on;`
    listen 443 ssl http2;
    server_name <YOUR_DOMAIN>;

    ssl_certificate     /etc/nginx/ssl/<YOUR_DOMAIN>.pem;
    ssl_certificate_key /etc/nginx/ssl/<YOUR_DOMAIN>.key;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_session_cache   shared:SSL:10m;
    ssl_session_timeout 10m;

    # 上传照片原片要放开 body 上限（与「设置」里的 upload.maxMb 是两回事，这里只是硬天花板）
    client_max_body_size 256m;

    # API：proxy_pass 末尾那个 `/` 负责剥掉 `/shaping-memory/api` 前缀，
    # 后端收到的仍是 /health、/settings、/files/:id/thumbnail 这些原生路径
    location /shaping-memory/api/ {
        proxy_pass http://127.0.0.1:3000/;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
    }

    # 后台静态文件（前缀匹配按「最长优先」，所以它一定比下面的前台块先命中）
    location /shaping-memory/admin/ {
        alias /var/www/shaping-memory-admin/;
        try_files $uri $uri/ /shaping-memory/admin/index.html;
    }

    # 少写尾斜杠时补一次跳转，否则页面内的相对资源会解析到上一层
    location = /shaping-memory/admin { return 301 /shaping-memory/admin/; }
    location = /shaping-memory       { return 301 /shaping-memory/; }

    # 前台静态文件
    location /shaping-memory/ {
        alias /var/www/shaping-memory-web/;
        try_files $uri $uri/ /shaping-memory/index.html;
    }
}
```

```bash
rm -f /etc/nginx/conf.d/shaping-memory-web.conf \
      /etc/nginx/conf.d/shaping-memory-admin.conf \
      /etc/nginx/conf.d/shaping-memory-api.conf
nginx -t && nginx -s reload
```

> 若服务器上还留着按子域名拆分时的旧配置（`listen 80 default_server` 加泛域名 `server_name`），
> 可保留作为网关保底；组成完整 URL 时以更精确的 `server_name <YOUR_DOMAIN>` 为准。
>
> **已知问题**：云服务器（阿里云 ECS 等）默认只放行 22/80，**443 要在控制台的安全组里
> 手动添加入方向规则**，否则表现是「服务器本地 `curl https://127.0.0.1/` 一切正常，
> 但公网访问直接超时」。在那之前可让 80 端口临时也提供完整服务（API 代理一起配上），
> 放行 443 后再把 80 块换回 `return 301`。

### ⚠️ 生产安全提醒

- **HTTPS 必须常开**。隐私分享链接的访问票据是明文放在 URL query 里的，
  纯 HTTP 部署下会被链路上的中间人截获 —— 所以 80 端口只保留 301 跳转，不提供保底页面。
- 域名或路径一旦变化，下面四处必须一起改，漏一处就会出现「页面能开、图片全裂」或登录态失效：
  1. `apps/web/vite.config.ts` 与 `apps/admin/vite.config.ts` 的 `base`；
  2. 两个前端打包时的 `VITE_API_BASE`（编译期注入，不重打包不生效）；
  3. 服务器 `.env` 的 `PUBLIC_BASE_URL` / `WEB_BASE_URL` / `CORS_ORIGINS`；
  4. nginx 的 `server_name`、`location` 前缀与 `proxy_pass` 剥前缀的尾斜杠。
- 证书到期前记得换新：本项目用的是单域名证书，直接替换
  `/etc/nginx/ssl/<YOUR_DOMAIN>.pem` 与 `.key` 后 `nginx -s reload` 即可。
- 数据库端口不要对公网开放，只绑 `127.0.0.1`。
- 生产库用独立账号与独立口令，口令在服务器上生成，不要经过任何传输通道。
- `.env`、`data/`、`tools/` 下的工具二进制都已在 `.gitignore` 中，上线前确认没有被带进仓库。

## 移动端打包

移动端是 Expo 应用，产出 Android 安装包用 prebuild + Gradle：

```bash
# 1. 装依赖（仓库根已装好的话可跳过）
npm install

# 2. 生成原生工程（android/ 目录，已 gitignore）
cd apps/mobile
EXPO_PUBLIC_API_BASE=https://<YOUR_DOMAIN>/shaping-memory/api npx expo prebuild --platform android --clean

# 3. 出 release APK
cd android && ./gradlew assembleRelease
#    产物：apps/mobile/android/app/build/outputs/apk/release/app-release.apk
```

> - `EXPO_PUBLIC_API_BASE` 必须在 prebuild/打包时注入，Expo 会把它内联进 bundle；
>   漏掉会让 App 去请求 `127.0.0.1`（真机上那是手机自己）。
> - 默认 release 包用 debug 签名，可直接安装检查；正式分发需自行配置签名密钥。
> - 需要 JDK 17 与 Android SDK（Platform 34+ / Build-Tools 34+），
>   可用 `npx expo-doctor` 检查环境。
> - Android 包名与 iOS bundle id 在 `app.json` 里（`cn.alsw.shapingmemory`），
>   改了要重新 prebuild。
> - **国内网络注意**：若 `services.gradle.org` 被透明拦截，Gradle wrapper 会报
>   `PKIX path building failed`（浏览器能下、Java 下不了）。把
>   `android/gradle/wrapper/gradle-wrapper.properties` 的 `distributionUrl`
>   换成国内镜像（如 `https://mirrors.cloud.tencent.com/gradle/`）即可。

### EAS 项目绑定（可选）

`app.json` 不携带任何 EAS 项目标识，该标识由 `apps/mobile/app.config.js`
从环境变量 `EXPO_PROJECT_ID` 注入。仅在使用 EAS Build / EAS Submit 时需要配置，
默认的 prebuild + Gradle 流程不依赖它：

```ini
# apps/mobile/.env（不入库，见仓库根 .gitignore）
EXPO_PROJECT_ID=<EAS_PROJECT_ID>
```

- 未配置时 `app.config.js` 原样返回 `app.json`，本地开发与打包行为不变；
  因此贡献者无需设置该变量，也不会误用他人的 EAS 项目。
- 该标识只表明构建归属于哪个 EAS 项目，**不携带任何凭据**。真正的凭据分别由环境变量
  （Expo 访问令牌）与 `apps/mobile/credentials/`（Android 签名密钥）承载，两者均不入库。
- 首次关联 EAS 项目可执行 `eas project:init`；若该命令把标识写回了 `app.json`，
  请将其移入 `.env` 并还原 `app.json`，保持仓库内配置中立。

## 数据库

- **表结构**：见 [`sql/`](sql/README.md)，与 `packages/db/src/schema.ts` 一一对应，
  16 张表按功能模块分为 7 个脚本，含完整建表语句、索引与约束。
- **日常改表**：改 `packages/db/src/schema.ts` 后执行 `npm run db:push`，不必手工写 SQL；
  再用 `npm run db:generate` 生成一条增量迁移留档，并**同步更新 `sql/` 脚本**，
  否则「从零重建」的路径会失真。
- **升级已有环境**：`npm run db:migrate` 应用尚未执行的迁移
  （迁移记录在 `packages/db/drizzle/`，接入方式见 [`sql/README.md`](sql/README.md) 的「结构变更与升级」）。
- **核心表**：`media`（照片主表）、`exif_metadata`（1:1 EXIF）、`tags` / `media_tags`、
  `categories`、`album_groups` / `albums` / `album_media`、`dictionary`（可枚举字段的候选值）、
  `users` / `roles` / `permissions` / `role_permissions`、
  `privacy_shares`（时效分享）、`settings`、`audit_logs`。
- **两条必须遵守的约定**：
  1. 分类是**文本关联**（`media.category` ↔ `categories.name`），故意不建外键，改名需在同一事务里同步两侧；
  2. 删除是**软删除**（`media.deleted`），所有业务查询都要带 `deleted = false`。

## 开发约定

- **语言**：代码注释、提交信息、界面文案统一中文。
- **类型**：`strict` 全开，禁止 `any`；新增依赖前先确认 `packages/` 里是否已有等价能力。
- **进程**：API 用 `ts-node` 启动且**不带 watch**，改完后端代码需要重启进程才生效。
- **图片**：前端不拼图片地址，一律用后端下发的 `url` / `cardUrl` / `originalUrl`；
  隐私照片的原片地址只在授权校验通过后才下发。
- **审计**：全局拦截器会给所有写操作留痕，且**强制剥掉 query** ——
  隐私票据（`?pt=`）和提取码不允许进日志表。新增写接口无需自己记日志。
- **设计**：颜色、字体、间距一律取自 `packages/design-tokens`，
  `npm run check:tokens` 会拦住硬编码；动效规范见 `docs/Motion-动效规范.md`。
- **路由顺序**：NestJS 按声明顺序匹配，`@Patch('batch')` 这类字面量路由必须写在 `@Patch(':id')` 之前。

## 贡献规范

完整的共建说明（环境搭建、仓库结构、开发约定、PR 流程、安全与隐私要求）见 [`CONTRIBUTING.md`](./CONTRIBUTING.md)；
以下为最常用条款的摘要：

1. **分支**：`feat/<简短描述>`、`fix/<简短描述>`，不直接往 `main` 推。
2. **提交前自检**（缺一不可）：
   ```bash
   npm run typecheck       # 四端类型检查必须全绿
   npm run check:tokens    # 动过样式就跑
   ```
3. **提交信息**：遵循 Angular 风格，说明「为什么」而不只是「做了什么」：
   ```
   feat(privacy): 支持为单张照片设置独立查看密码
   fix(web): 修复分享页验证失败后按钮卡在「验证中」
   ```
4. **不要提交**：`.env`、`data/`、`tools/exiftool/` 下的工具二进制、任何真实口令与密钥、含个人信息的照片。
   提交前可用 `git status` 与 `git diff --staged` 再确认一遍。
5. **改到数据库**：`schema.ts` 与 `sql/` 脚本要一起改；破坏性变更（删列 / 改类型）需在 PR 说明里写清迁移方案。
6. **改到 API 契约**：同步更新 `packages/sdk` 的类型，三端会用同一份。
