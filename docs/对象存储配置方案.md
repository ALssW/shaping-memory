# 塑忆 · 对象存储配置方案（S3 兼容 · 简化版）

> 本文取代此前的《阿里云 OSS 专题方案》。旧版要求使用者先完成 RAM 细粒度策略、生命周期规则、
> 双桶规划、CDN 防盗链等一长串控制台操作，对不熟悉云服务的普通用户时间成本过高。
>
> 本版遵循「最小可用」：**只配 5 个字段，只做 4 件事**；默认零配置也能把项目完整跑起来。

---

## 0. 一句话结论

| 场景 | 怎么做 |
| --- | --- |
| 我就想先跑起来 | **什么都不用配**。`STORAGE_PROVIDER` 默认 `local`，照片与生成物都留在本机 `STORAGE_DIR` |
| 我想省磁盘 / 做异地副本 | 改成 `s3`，填 5 个配置项 + 2 个密钥，其余交给接口 |
| 隐私照片 | **同样上云**（桶保持私有、照片地址永不出 URL、API 全代理）。不再做「只留本机」的物理隔离（见 §4） |
| 上什么云、留什么本机 | **混合存储**：原片 + 实况视频上云；缩略图 / 卡图 / 模糊图恒留本机（见 §3、§5） |

> **切到 `s3` 之前必须先跑一次 `npm run backfill:objects`**，把存量照片的原片补上云，
> 否则老照片的原片与实况会直接 404（见 §9）。

## 1. 配置项

配置模板与 `.env` 的对应关系（概念配置 → 环境变量）：

```jsonc
{
  "storage": {
    "provider": "s3",                    // → STORAGE_PROVIDER      （local | s3，默认 local）
    "bucket": "your-photos-bucket",      // → STORAGE_BUCKET        （s3 必填）
    "region": "us-east-1",               // → STORAGE_REGION        （s3 必填）
    "prefix": "photos/",                 // → STORAGE_PREFIX        （可选，所有操作都在它下面）
    "customDomain": "cdn.yourdomain.com" // → STORAGE_CUSTOM_DOMAIN （可选，填了才生成图片直链）
  }
}
```

环境变量（与上表一一对应，另加两项）：

| 环境变量 | 必填 | 说明 |
| --- | --- | --- |
| `STORAGE_PROVIDER` | 否 | `local`（默认）/ `s3` |
| `STORAGE_BUCKET` | s3 必填 | 桶名 |
| `STORAGE_REGION` | s3 必填 | 区域，如 `us-east-1`、`cn-hangzhou` |
| `STORAGE_PREFIX` | 否 | 公共前缀，如 `photos/`；留空表示直挂桶根 |
| `STORAGE_CUSTOM_DOMAIN` | 否 | 自定义域名；**留空最省事**，图片全部由 API 转发 |
| `STORAGE_ENDPOINT` | 否 | 服务地址。AWS 官方留空；阿里云 OSS / MinIO / R2 **必填** |
| `STORAGE_PATH_STYLE` | 否 | 寻址风格。`true`（默认）= path-style，自建 MinIO 用；`false` = virtual-hosted，**阿里云 OSS 等托管服务必须填 `false`**，否则 403 |
| `S3_ACCESS_KEY_ID` | s3 必填 | 访问密钥 ID |
| `S3_SECRET_ACCESS_KEY` | s3 必填 | 访问密钥 |

> `STORAGE_ENDPOINT` 与 `STORAGE_PATH_STYLE` 是这张表里仅有的两项「额外项」：
> S3 协议既不规定服务地址长什么样（AWS 能从 region 推出，其他服务商推不出来），
> 也不规定桶名放在路径还是子域名里。二者都不引入新概念，各填一个值即可。

### 1.1 密钥安全

- 密钥**只从环境变量读取**，不写进代码、不写进仓库；`.env` 已在 `.gitignore` 中，权限建议 `600`。
- `describe()` 与启动日志**永不输出密钥**，只输出桶名 / 区域 / 前缀 / 域名。
- 建议使用子账号密钥，权限只给这一个桶的读写，不要用主账号密钥。
- 选了 `s3` 却漏填必填项时，启动会直接报：

  ```
  已选择对象存储（STORAGE_PROVIDER=s3），但还缺少：STORAGE_BUCKET、S3_ACCESS_KEY_ID
  ```

  （四项一次报全，不用配一个报一个来回重启。）

## 2. 接口：只有 7 个动作

定义见 [packages/storage/src/index.ts](file:///d:/dev/project/application/shaping-memory/packages/storage/src/index.ts)。

| 方法 | 作用 |
| --- | --- |
| `put(key, body, contentType?)` | 写入（覆盖同名对象） |
| `get(key, range?)` | 读取为**可读流**，不整块进内存；可带 Range 取片段，供实况视频拖动进度条 |
| `exists(key)` | 判断存在性（只发元数据请求，不拉内容） |
| `remove(key)` | 删除，**幂等**：对象本来就不在也算成功 |
| `list()` | 列出公共前缀下的全部对象（自动翻页取完） |
| `url(key)` | 生成对外直链；未配 `customDomain` 时返回 `null`，上层退回 API 中转 |
| `describe()` | 一句话描述当前存储形态，**已脱敏**，可安全写日志 |

设计要点：

- **`prefix` 自动处理**：调用方写 `thumbs/a.jpg` 或 `/thumbs/a.jpg` 都对，前缀拼接收敛在接口内部一处完成，
  上层不必各自记得「到底要不要带斜杠」。
- **`key` 永远是相对键**：`list()` 返回的键同样已去掉前缀，可以直接回喂给 `put` / `get` / `remove`。
- **键来自请求参数时做路径穿越校验**（本机实现里），`../../` 读不到根目录之外的文件。
- 刻意**不做**分片上传、生命周期、版本控制、跨区复制、断点续传。每多一个旋钮，
  就多一处「配错了却不知道错在哪」的可能 —— 需要时再作为二期能力单独引入。

### 2.1 错误处理

所有失败统一抛 `StorageError`：

```ts
class StorageError extends Error {
  code: 'not_found' | 'denied' | 'unreachable' | 'unknown';
  message: string;   // 给用户看的中文，不含密钥与上游原始错误
  cause?: unknown;   // 原始错误，只用于写日志
}
```

| `code` | 面向用户的说法 | 实际含义 |
| --- | --- | --- |
| `not_found` | 这个文件在存储服务里找不到 | 键不存在 / 404 |
| `denied` | 上传被存储服务拒绝，请检查访问密钥与桶权限 | 密钥错、权限不足、签名不符、403 |
| `unreachable` | 连不上存储服务，请检查服务地址与网络 | DNS / 连接被拒 / 超时 |
| `unknown` | 上传失败 | 其余情况 |

技术细节（HTTP 状态码、SDK 错误名）只进 `cause` 供排查，**不会出现在给用户看的文案里**。

## 3. 键（Key）约定

`key` 都是相对 `STORAGE_PREFIX` 的路径，用 `/` 分隔：

| 对象 | 键 | 存放位置 |
| --- | --- | --- |
| 原片 | `originals/{mediaId}{扩展名}` | ✅ **云端**（本机仅 PHOTO_SOURCE_DIR 里的档案本体） |
| 实况内嵌视频 | `live/{mediaId}.mp4` | ✅ **云端**（导入后本机副本被回收） |
| 详情档缩略图 | `thumbs/{mediaId}.jpg` | ❌ **只留本机** |
| 卡片档缩略图 | `thumbs/{mediaId}-card.jpg` | ❌ **只留本机** |
| 隐私模糊图 | `blur/{mediaId}-v{版本}s{强度}.jpg` | ❌ **只留本机** |

模糊图键里的算法版本号是既有约定，升级模糊算法后旧缓存必须自然失配，否则会静默沿用旧图。

> **为什么衍生品留本机**：缩略图 / 卡图 / 模糊图是最热的展示端点，留在本机可以直接交给
> express 的 `sendFile` —— Range / ETag / 304 免费且零云端带宽；而它们体积极小（见 §5），
> 留在本机几乎不占磁盘。原片占全部字节的约 97%，把它推上云才是省磁盘的关键。
>
> **键不落库**：几个键都能由 `media` 行推导（`id` + 源文件扩展名 + 是否有实况视频，见
> [photo-objects.ts](file:///d:/dev/project/application/shaping-memory/apps/api/src/photo-objects.ts)），
> 因此不加数据库列、不做迁移。历史上传过的 `thumbs/` 云端副本不再写入，但清理逻辑仍会一并删除（`removePhotoObjects`）。

## 4. 混合存储 + API 代理：隐私照片也上云

本版把「隐私照片只留本机」的旧铁律**取消**了：切云之后，隐私照片的原片同样进对象存储。
隐私性改由**代理层**承担，而不是靠物理隔离。守住它需要同时满足：

1. **桶必须私有**，**不要**给这个桶绑任何公开 CDN 域名 —— 这是整套隐私模型的地基。
2. **照片地址永不出 URL**：接口只回 `/files/{id}/...` 这类同域路径，桶的直链
   （`originals/{id}.jpg` 或预签名 URL）一律不下发给前端，因此无需防盗链与签名时效管理。
3. **字节的去留只由 `gate()` 说了算**：代理层按「当前访客能不能看这张」判定，
   受保护时缩略图 / 卡图改写为模糊图、原片 / 实况直接 403，
   获准下发的隐私原片一律 `Cache-Control: private, no-store`（连浏览器自己都不许留痕）。

也就是说：判断权始终在 API 手里，桶只是「存字节的地方」，即便有人拿到了桶的读权限，
也无法从公网直接访问到任何一张照片。这与「公开桶 + 直链」相比只多了一次转发，
却省掉了整套防盗链 / 边缘缓存配置，且不依赖任何服务商特性。

### 写什么、不上什么

- **上传时不再做隐私判定**：只要不是本机模式，原片与实况视频一律推云（判定见 `photo-objects.ts`）。
- **否定旧的「标记为隐私就删云端副本」**：隐私标记只影响**出口行为**，不再触发删除。
- 软删除的照片云端副本保留（软删除可回滚）。

## 5. 尺寸规格与「原片上云、衍生品留本机」的可行性

各产物的大致规格（手机直出原片口径，实际因机型而异）——**原片占了约 97% 的字节**，
这正是把它推上云、衍生品留本机的依据：

| 产物 | 长边 / 尺寸 | 常见文件大小 | 存放 |
| --- | --- | --- | --- |
| 原片 | 原始分辨率（如 4000×3000 / 6000×4000） | **6–12 MB** | 云端 |
| 详情档缩略图 | 长边 1280 | 100–350 KB | 本机 |
| 卡片档缩略图 | 长边 640 | 25–90 KB | 本机 |
| 模糊图（占位） | 长边 640（先降采样再放大，细节已物理消失） | 4–20 KB | 本机 |
| 实况内嵌视频 | 与照片同分辨率的一小段 MP4 | 1–5 MB | 云端 |

**结论：可行。** 假设 1 万张照片：

- 原片 + 实况：约 60–120 GB（上云，省下的主要磁盘）
- 缩略图 + 卡图：约 1.3–4.4 GB（本机；详情档 + 卡片档各一份）
- 模糊图：约 0.04–0.2 GB（本机，仅为隐私照片生成）

本机只需承担约 1.5–4.6 GB（≈ 总量的 3%），省下了绝大多数磁盘；同时最热的展示端点
（缩略图 / 卡图）仍走本机 `sendFile`，不消耗云端带宽，也无需为它们做代理与鉴权。

## 6. EXIF 模型：数据库是唯一事实源

**云端原片自上传起不可变，EXIF 的一切修改只落数据库。**

| 环节 | 做法 |
| --- | --- |
| 导入 / 上传 | 上云**之前**先用 exiftool 抽全量 EXIF，写进 `exif_metadata.extra`（`-n` 原始口径） |
| 后台编辑 | `PATCH /photos/:id/exif` 只改 `exif_metadata`；原片文件（云端对象 / PHOTO_SOURCE_DIR 档案）保持原样 |
| 下载原片 | `GET /files/:id/download` 在**临时副本**上写入库里最新的 EXIF 再下发，原片不动 |
| 展示 | 前台 / 后台的 EXIF 展示一律读数据库，与「文件里有什么」解耦 |
| 查看原片 EXIF | `GET /photos/:id/original-exif` 只读解析**原片本体**（不写库、不改文件），供与库里记录对照 |

好处：编辑永远可逆、不依赖任何云端写能力、不需要为原片做备份；代价是「带新 EXIF 的文件」
只在下载那一刻才生成（这是刻意的 —— 展示与下载是两条不同语义的出口）。

## 7. 各服务商速查

| 服务商 | `STORAGE_ENDPOINT` | `STORAGE_REGION` | `STORAGE_PATH_STYLE` | 备注 |
| --- | --- | --- | --- | --- |
| AWS S3 | 留空 | 如 `us-east-1` | 不用填 | 官方地址可由 region 推出，默认走 virtual-hosted |
| 阿里云 OSS | `oss-cn-hangzhou.aliyuncs.com` | `cn-hangzhou` | `false` | 服务器与桶同区域时可用 `oss-cn-hangzhou-internal.aliyuncs.com`，流量免费 |
| MinIO（自建） | `http://192.168.1.10:9000` | 任意（如 `us-east-1`） | `true` | endpoint 需带 `http://` 或 `https://` |
| Cloudflare R2 | `https://<账号ID>.r2.cloudflarestorage.com` | `auto` | `false` | 密钥在 R2 控制台创建 |

`STORAGE_PATH_STYLE` 决定桶名写在哪儿：`true` 是 `endpoint/bucket/key`，`false` 是
`bucket.endpoint/key`。自建服务（MinIO）用前者可免去为每个桶配 DNS 与证书；
**阿里云 OSS 只认后者**，用 path-style 访问会直接被拒：

```
403 Please use virtual hosted style to access.
```

`STORAGE_ENDPOINT` 只写域名（如 OSS 文档里的 `oss-cn-hangzhou.aliyuncs.com`）也没关系，
代码会自动补上 `https://`（见 [packages/storage/src/index.ts](file:///d:/dev/project/application/shaping-memory/packages/storage/src/index.ts) 的 `normalizeEndpoint`）——
但**不要写 path 部分**，SDK 的 endpoint 只接受协议 + 主机名。

## 8. 启动时怎么确认配好了

API 每次启动都会打印一行脱敏摘要：

```
[shaping-memory api] storage: s3, bucket=your-photos-bucket, region=us-east-1, prefix=photos/, endpoint=oss-cn-hangzhou.aliyuncs.com
```

- 看到 `local(root=/opt/shaping-memory/data)` → 用的是本机存储，符合默认预期。
- 看到 `s3, ...` → 对象存储配置已被识别。**这里不会出现密钥**。
- 配置有遗漏时，进程会在启动阶段直接报错并指出缺哪个变量，不会带着错误配置默默跑起来。

## 9. 当前进度与二期可选

> ⚠️ **切到 `STORAGE_PROVIDER=s3` 之前，必须先跑一次 `npm run backfill:objects`。**
> 切换后原片 / 实况不再读本机文件（本机已无字节），没上过云的存量照片会直接 404。
> 该命令只处理 `deleted = false` 的照片（含隐私照片），把 `originals/` 与 `live/` 补上云，
> 并一并补齐 `exif_metadata.extra`，成功后才回收本机副本（`uploads/` 暂存与 `live/`）。
> PHOTO_SOURCE_DIR 里的档案本体一个字节都不删。

**已落地：**

- 存储接口与两种实现（本机 / S3 兼容）：`packages/storage`
- 环境变量与「选了 s3 但漏填」的启动校验：`packages/config`
- 启动时的脱敏存储摘要：`apps/api/src/main.ts`
- **混合存储**：导入（`npm run import:photos`）与后台上传时，只有**原片 + 实况视频**推云
  （见 `apps/api/src/photo-objects.ts`）；缩略图 / 卡图 / 模糊图恒留本机。
  上传失败**不阻断导入**，只在 CLI 汇总里报「未上云」的明细。
- **读取已接入混合 + API 代理**：`/files/{id}/thumbnail|card|blur` 恒本机 `sendFile`；
  `/files/{id}/original|live` 本机走 `sendFile`、云端从桶取回后流式转发（支持 Range / ETag / 304）。
  照片地址永不出 URL，隐私照片也上云（见 §4）。
- **EXIF 以数据库为唯一事实源**：导入时抽全量 EXIF 存 `exif_metadata.extra`，
  编辑只改库，下载时（`GET /files/:id/download`）才把最新 EXIF 注入临时副本下发；
  后台「查看原片 EXIF」（`GET /photos/:id/original-exif`）只读解析原片本体（见 §6）。
- **前台原片出口已接线**：查看器 EXIF 卡片右下角「加载原片」（`?inline=1` 就地显示、不落盘）
  与「下载」（attachment 落盘）走**同一份字节** —— 都是注入了库里最新 EXIF 的原片。
  两个地址由 sdk 从 `originalUrl` 派生，隐私票据因此自动带上。

**尚未接入（需要单独一次改造）：**

- **存量照片迁移**：本次只让**新导入 / 新上传**与 `backfill:objects` 覆盖存量；
  若担心遗漏，可再跑一次 `npm run import:photos`（幂等，只会把缺的对象补上）。
- 软删除照片的云端副本保留（软删除可回滚）；键里含 `mediaId`（源文件名的哈希），不可猜，
  但**不要**给这个桶绑公开 CDN 域名（见 §4）。

每一批改造都能独立回滚：把 `STORAGE_PROVIDER` 改回 `local`，读取立刻回到本机文件，
对象存储里已上传的副本留着不影响任何行为。

**二期可选（现在都不要做）：**

CDN 加速、生命周期规则、版本控制、跨区域复制、分片上传、图片处理参数。
等你真的遇到「磁盘不够」或「访问太慢」时再逐项引入，一次引入一项。
