# Motion 动效规范（Web）

> 本规范是 Web 端**动效实现的唯一入口**，与 [`设计语言-Token规范.md`](./设计语言-Token规范.md) 配套：
> Token 规范定「动效的数值」，本规范定「谁来动、怎么动、哪些情况下不许动」。
>
> - **动效库**：[Motion](https://motion.dev)（前身 Framer Motion），`motion@^12`
> - **参数来源**：[`packages/design-tokens/tokens.json`](../packages/design-tokens/tokens.json) 的 `motion.*`
> - **基线层**：[`apps/web/src/lib/motion.ts`](../apps/web/src/lib/motion.ts)
> - **校验**：`node packages/design-tokens/scripts/check-tokens.mjs`

---

## 1. 为什么要用 Motion

CSS 动画能表达的只有「从 A 状态到 B 状态」。而本项目的几处关键动效本质上都是**手势驱动**或
**状态耦合**的：

| 需求 | CSS 做不到的地方 |
| --- | --- |
| hover 时邻位照片按距离朝悬浮那张聚拢 | 需要知道每张照片与 hover 那张的真实几何距离 |
| 指针在照片框内移动产生附着位移 | 需要逐帧读取指针相对位置，并带惯性 |
| 点击照片从网格位置放大到全屏 | 需要拿到两端的真实矩形，并在退出时反向飞回 |
| 缩略图导航条的选中标记滑到下一枚 | 需要一个元素在**两个位置之间**连续移动，而不是各自闪烁 |

这些都要读 DOM、要跨组件共享状态、要可中断可反向 —— 交给 Motion，CSS 只保留「绘制类」属性的静态定义。

---

## 2. 职责边界（先记住这一条）

**Motion 负责合成层属性（transform / opacity / 位置尺寸），CSS 负责绘制类属性（阴影 / 圆角 / 底色 / 字体）。**

| 属性 | 归谁 | 理由 |
| --- | --- | --- |
| `transform`、`opacity` | Motion | 不触发布局与重绘，可全程走 GPU 合成层 |
| `width/height/left/top`（查看器画框） | Motion | 全屏模态里只有一个元素，且两端矩形是算出来的 |
| `box-shadow` | CSS | 阴影里含 `color-mix()` 与 `var(--color-accent)`，**Motion 无法插值** |
| `border-radius` | CSS | 不需要逐帧插值，`transition` 足够 |
| `background`、`color`、`border-color` | CSS | 同上；它们是「状态」，不是「运动」 |
| 图片加载完成后的淡入 | CSS | 它不是交互动效，是资源就绪提示 |

> **一句话**：想知道某个属性该归谁，就看它是否需要「逐帧数值 + 时序控制」。
> 需要就交给 Motion，不需要就留在 CSS。

## 3. 基线层：所有参数只从 token 取

Motion 的过渡是 **JS 值**，不能像 CSS 那样写 `var(--motion-spring-smooth)`。
如果每个组件各写一份 `{ type: 'spring', duration: 0.4, bounce: 0.15 }`，等于把 token 抄了 N 遍，
迟早与 `tokens.json` 不一致。因此所有过渡都在 [`lib/motion.ts`](../apps/web/src/lib/motion.ts) 里派生一次：

```ts
import { tokens } from '@shaping-memory/design-tokens';

/** token 里的时长是 '200ms' 字符串，Motion 只认秒 */
const toSeconds = (value: string) => Number.parseFloat(value) / 1000;

/** 非空间状态：淡出淡入、颜色过渡 */
export const fade = (key: keyof typeof tokens.motion.duration = 'base'): Transition => ({
  duration: toSeconds(tokens.motion.duration[key]),
  ease: bezier(tokens.motion.easing.smooth),
});

/** 空间运动：tokens.motion.spring.* 的形状（duration + bounce）与 Motion 完全同构 */
export const spring = (key: keyof typeof tokens.motion.spring = 'smooth'): Transition => ({
  type: 'spring',
  duration: tokens.motion.spring[key].duration,
  bounce: tokens.motion.spring[key].bounce,
});
```

**组件里禁止出现手写的 `duration` / `ease` / `bounce` 数字。** 需要新档位时，先在
`tokens.json` 加 token，再同步两端产物，最后跑校验 —— 与 Token 规范的变更流程完全一致。

### 3.1 可用的导出

| 导出 | 用途 |
| --- | --- |
| `fade(key?)` | 非空间状态档位：`fast`(150ms) / `base`(200ms) / `slow`(300ms) |
| `spring(key?)` / `springs.smooth\|snappy\|bouncy` | 空间运动档位 |
| `springOptions(key?)` | `useSpring` 钩子专用（钩子只接受 `duration` / `bounce` 简写） |
| `INSTANT` | 拖动跟随时显式关掉补间 |
| `HOVER_LIFT` / `HOVER_LIFT_Y` / `PRESS_SINK` | 手势配方：1.05 / −6px / 0.985 |
| `ATTACH_RANGE` | 指针附着位移半径 7px（挂在卡片本身上） |
| `PUSH_RANGE` / `PUSH_RADIUS` / `PUSH_FLOOR` | 聚拢上限 5px / 衰减半径 2.2（单位是「一个卡片宽」）/ 保底力度 0.4 |
| `pushFalloff(gap)` | 聚拢强度：按归一化距离线性衰减，衰减到 `PUSH_FLOOR` 为止（只有自己那张是 0） |

### 3.2 全局保底：`MotionConfig`

[`App.tsx`](../apps/web/src/App.tsx) 最外层挂了 `MotionConfig`，它替所有组件统一处理两件事：

```tsx
<MotionConfig reducedMotion="user" transition={springs.smooth}>
```

1. **默认过渡**：没单独写 `transition` 的动画自动落到 `spring.smooth`；
2. **`reducedMotion="user"`**：用户在系统里开了「减少动态效果」时，Motion 自动停掉
   transform / 布局动画、只保留透明度变化。**因此组件里不需要逐个判断 `prefers-reduced-motion`。**

## 4. 动效清单

下表是 Web 端**全部**动效。新增动效必须补进这张表。

### 4.1 照片：抬起 / 附着 / 聚拢

实现：[`PhotoTile.tsx`](../apps/web/src/components/PhotoTile.tsx)（墙面卡片）、
[`hooks/useRipple.ts`](../apps/web/src/hooks/useRipple.ts)（聚拢量的来源）。列表卡片不参与聚拢，
hover 只用 CSS 加厚一档材质（属于 §4.5 那类纯状态反馈）。

| 动作 | 表现 | 参数 |
| --- | --- | --- |
| 指针进入（墙面卡片） | 卡片缩放 `HOVER_LIFT`(1.05) **并向上抬起** `HOVER_LIFT_Y`(−6px)；照片长在卡片里，**同比放大同一档** | `springs.smooth` |
| 指针移动 | **整张卡片**（照片框）朝指针那一侧挪动：位移 = 指针相对中心的偏移 × `ATTACH_RANGE`(7px) | `useSpring(springOptions('smooth'))` |
| 指针离开 | 附着归零 → 卡片回落，即「**下沉**」 | `springs.smooth` |
| 极短按压 | 缩到 `PRESS_SINK`(0.985)（由 `pressed` 状态驱动，不再是 `whileTap`） | `springs.smooth` |
| **邻位聚拢** | 周围照片沿「自己与悬浮张的连线」**朝它靠拢**，一次性；距离越远越轻、但**全屏每一张都动** | `pushFalloff(gap)` × `PUSH_RANGE`(5px) |
| 蒙版显隐 | `.photo-card__overlay` 透明度 0↔1（**文字层不参与放大**） | `fade()` |

**墙面为什么「先分段、再在段内轮转分列」**：一是 multi-column 是**列优先**填充，
它会把最新的一整段排入第一列，于是横向紧邻的两张在时间上可能差着好几个月
（实测第 1 列 2026-08、第 5 列 2023-01）。二是**纯轮转分列**（整份列表直接按
「第 i 张进第 i % N 列」摊进 N 条贯穿整页的纵列）虽然横读即时间序，但各列的刻度边界
位置天生不同步 —— 分隔线只能退化成「每列各拉一条短线」，画不出列表那样横贯整行的一根线。
因此 `WallView` 改为**两段式**：先按当前刻度把有序列表切成段，每段渲染
「一条整行分隔线（`.masonry__time-sep`，与列表 `.list__group-head` 同款）+ 一个 N 列子网格」，
段内再轮转分配（`第 i 张进第 i % N 列`）—— **横向读过去就是时间推进的方向**，
整段像文字一样「先从左往右、再往下」；段与段之间由那根整行线切开。
代价是段高不再自动均衡（各列按自身内容收尾），且**张数不足一行的段右侧会留白** ——
这是「按时间从左往右 + 一根横贯整行的分割线」必须付的那部分（列表的小分组同样如此）。
列数由 JS 给到 `--masonry-cols`：分配方式在 JS 里做，列数就必须与它同源，
否则「谁进哪一列」和「有几列」会各说各话（断点仍是 1440 / 1024 / 769 → 5 / 4 / 3 / 2 列）。
副作用是**段内** DOM 顺序变成列优先：聚拢必须靠 `data-index` 认卡片（见下方「聚拢为什么由父级算」）。

**照片为什么不再单独缩放**：它长在卡片里，卡片放大时照片跟着同比放大 —— 两者是同一个变换矩阵，
天生同步。曾试过「卡片放大 + 照片反向缩放」以突出容器，代价是照片在屏幕上尺寸恒定、
放大只体现在卡片四周的装裱边，放大感太弱（且两条独立弹簧实测会错位到 9.9px）。

**附着为什么挂在卡片上、而不是内层照片**：需求是「照片框随鼠标轻微附着」。只动内层会读成
「框不动、里面的照片在滑」—— 框是这张照片的边界，边界不动就没有「被拿在手里」的感觉。

**聚拢为什么由父级算**：每张卡片只知道「我该被拉多少」，不知道别人在哪。距离在 hover 切换时
用真实几何量一次 —— 瀑布流是「时间分段 + 段内 N 条轮转纵列」，**段内 DOM 顺序是列优先**，该排布下「DOM 相邻」
既不等于「视觉相邻」也不等于「索引相邻」。因此几何数组**按卡片自带的 `data-index` 归位**，
而不是按它在 DOM 里的出现次序（`PhotoTile` 把时间下标原样落到 `data-index` 上）。
滚动与筛选期间零测量。

**聚拢的作用范围**：整个瀑布流（`WallView` 持有状态）。`PUSH_FLOOR` 让衰减有下限，
因此屏幕另一侧的卡片同样会动 —— 「全屏所有照片同步跟随」靠的就是这个保底档，
而不是把半径调大（半径调大只会让近处过冲）。

**为什么是「径向平移」而不是「缩放」**：缩放会把邻位自己的内容也放大，读起来是「周围也变大了」；
径向平移只动位置、不动内容，才是「被吸引过去」。方向与大小由同一次除法给出
（`单位向量 × 力度`），省掉一次归一化。

**只有悬浮那张跟随指针**：附着（`useMotionValue` + `useSpring`）只挂在当前 hover 的卡片上，
指针离开即归零，邻位只有「被吸引的固定位移」、不含指针项。指针在两张卡片之间移动时，
邻位的位移量因此是常量，不会跟着指针抖（几何也刻意读 `offset*` 布局值，见 §5 第 3 条）。

**同一个 transform 上的两股位移怎么合**：卡片的 `x / y` 由三个来源相加 ——
邻位聚拢、抬起（两者离散，只在 hover 切换时才变）与指针附着（逐帧）。
同一个属性上的 `animate` 与 `style` 会互相覆盖，因此三者都做成 `MotionValue`：
离散的那股（聚拢 / 抬起 / 缩放）用命令式 `animate(value, target, springs.smooth)` 驱动，
附着的读数直接喂给 `useSpring`，最后用
`useTransform<number, number>([a, b], ([x, y]) => x + y)` 相加后统一交给 `style`；
`animate=` 属性在整个组件里一处都不用（不与 `style` 抢属性）。

**离散位移为什么用命令式 `animate()`、不用 `useSpring(...).set()`**：后者实测不认
`tokens.motion.duration` 的档位 —— 给 `useSpring` 出的 `MotionValue` 赋值走的是
`motion-dom` 的内部跟随（`attachFollow` 建一个 `FollowAnimation`），8px 的聚拢两三帧
就到位（≈47ms），而同参数的 `animate()` 是 400ms。聚拢本该是「平滑靠拢、平滑归位」，
快 8 倍就没有弹簧可言了。代价是 `animate()` 会把补间引擎拉进包体（实测 gzip +4 KB），
换取的是「离散位移与视觉预期一致」，值得。

### 4.2 查看器：点击放大 / 反向缩回

实现：[`Viewer.tsx`](../apps/web/src/components/Viewer.tsx)

| 动作 | 表现 |
| --- | --- |
| 点照片 | 画框从「网格矩形」补间到「安全区居中的矩形」，即放大 |
| 点照片以外任意处 / `Esc` | 反向：画框飞回**当前这张**在网格里的矩形，播完才卸载 |
| 翻页 / 点缩略图 | 画框按新照片的纵横比重算落点 |
| 打开 | EXIF 卡片从照片右缘后方滑出（从 −100% 到 0），与画框同一根弹簧 |
| 关闭 | EXIF 卡片原路收回照片背后，再随画框一起飞回网格 |
| 背板 | 单独一层淡入淡出 |
| 关闭 | **页头 / 箭头 / 胶片条跟着 `leaving` 一起淡出**，与画框的飞行同时发生（不是等画框落地、节点卸载时才「啪」地消失） |

两端矩形都是 JS 算出来的（**确定性 FLIP**），不依赖库的布局投影：

- 起点：`PhotoTile` 激活时把 `.progressive` 的视口矩形交给上层（`OpenHandler` 的第三个参数）
- 终点：`fitRect(aspect, viewport)` —— 把「按纵横比撑开的盒子」装进安全区并居中，
  并**先把 EXIF 卡片的位置扣掉**：宽屏扣右侧的「间隙 + 卡片宽」，窄屏扣下方的「间隙 + 卡片高」，
  于是「照片 + 卡片」作为一个整体居中，照片不会被卡片压住
- 安全区：`SAFE_TOP`(60) / `SAFE_SIDE`(40) / `SAFE_BOTTOM`(= space-64 + 胶片条高 85 + space-24 ≈ 173)，
  **必须与 `app.css` 里 `.viewer__close`、`.viewer__stripbox` 的留白与 `--strip-dot` 一致**
  （原 `viewer__top` 页头已移除，顶部 60 的留白留给右上角的关闭按钮）；
  卡片的 `EXIF_W` / `EXIF_H` / `EXIF_GAP` 同理与 `.viewer__frame` 上的两个 CSS 变量一致
  （与 `useProgressRail` 的 `TL_LINE` 是同一类约定：CSS 量在 JS 里只留这一份镜像）

**照片内的 2× 放大与拖曳**（与「画框飞进安全区」是两件事，互不干扰）：

| 动作 | 表现 |
| --- | --- |
| 点击照片（未放大） | 以**指针位置**为中心放大到 2×，画面朝你点的地方推近 |
| 已放大 · 按住左键拖动 | 平移画面，1:1 跟手；松手即暂停，再按住继续 |
| 已放大 · 按下但**没拖动**就松开 | 这一下算「点击」→ 缩回 1×（`Esc` 同效） |
| 拖动中 | 光标切 `--cursor-drag`（动态区域 AF：绿框外环绕 8 枚小点）；`transform` 的补间**关掉**（优先保证跟手性） |

- **点击 vs 拖曳靠 4px 位移阈值**（`DRAG_SLOP`）区分：拖过之后再松手不会被误判成缩小。
- **变换写在 `<img>` 上，不写在外层容器上**。容器的布局盒因此保持未缩放的尺寸，
  `getBoundingClientRect()` 始终是稳定参照 —— 位移换算与边界夹取都靠它；
  若变换挂到容器上，量到的就是放大后的框，换算会自我叠加。
- **边界夹取**（`clampPan`）：平移量上限 = 画框尺寸 × (倍率 − 1) / 2，
  即「放大后多出来的那圈」的一半。超出就会在画框里露出底色，因此必须夹住。
- 位移是**逐帧数值**（§2 判据）→ 交给 React state + CSS `transform`，
  拖动中不给过渡；容器自身的缩放/位置仍由 Motion 的 FLIP 负责，两者不共用属性。

**背板为什么单独成层**：若把不透明度放在最外层容器上，画框会被一起淡掉 ——
照片飞回网格的途中背板先退场，画面才连贯。

**「框外之壳」为什么也走 `leaving` 这条淡出**：关闭按钮、翻页箭头、胶片条都不是画框的一部分。
若只让它们在节点卸载时一起消失，观感是「照片缩完了、再闪一下」；接上同一条 `leaving` 后，
它们与画框的飞行**同时**渐隐，退场读起来是一件连续的事（`is-leaving` 同时把这三块的
`pointer-events` 关掉，退场途中不会误触）。

**EXIF 卡片为什么要一层裁切窗**：卡片平时要「藏起来」，但它与照片并排、不能真的消失
（消失就得等动画回来）。`.viewer__exifclip` **紧贴画框右缘**（`left: 100%`，不留缝；窄屏改挂下缘）、
`overflow: hidden`，卡片自身位移 `−100%` 时正好整个躲进窗外，滑到 `0%` 才露出来。
位移用**百分比**而不是像素，于是它自动等于卡片宽度，JS 侧不需要再镜像一份尺寸。

**那道「卡片与照片之间的间隙」是动画的一部分、不是写死的定位**：窗口自己承担这段位移 ——
就位时从 `0` 滑到 `EXIF_GAP`，关闭时反向滑回 `0`。两端因此是「起点紧贴照片右缘、
终点让开一格」，中途露出的永远只是窗口里那一条。曾把间隙写进 `left: calc(100% + gap)`，
结果是关闭时卡片被锚在「照片右缘 + gap」处缩成一条黑竖线、还挡着右边那张照片，缩到 0 才消失。
卡片高度取 `height: 100%`（= 画框高）—— 照片多高它多高，内容装不下时卡内滚动，绝不撑高画框。

### 4.3 缩略图导航条：选中标记「飞」过去

实现：`Viewer.tsx` 的 `.viewer__stripbox`

选中标记（`.viewer__dotring`）是一个带 `layoutId="viewer-dot-ring"` 的元素，只挂在当前缩略图上。
切换时 Motion 让它从上一枚的位置连续移动到下一枚，而不是各自闪烁；缩略图本身用
`animate={{ scale: isOn ? 1.5 : 1, opacity: isOn ? 1 : 0.5 }}` 配合 `springs.snappy`。

**一次只摆 20 张**：胶片条渲染的是以当前这张为中心的**滑动窗口**
（`start = clamp(index − 10, 0, n − 20)`，两端夹边），而不是整卷铺开 ——
50+ 张全铺出来既读不出「相邻几张」，也得靠横向滚动去找当前那张。
窗口滑动的代价是「当前这张在窗口里的序号」会变，因此滚动定位取 `children[index − start]`，
不能再直接用 `index`。

**滚轮在这条上是「翻页」，不是「滚动」**：一次滚动操作会连发几十个 `wheel` 事件，
因此加一道 `WHEEL_LOCK_MS`(180) 时间锁 —— 一次手势只走一张，否则一滑跳过十几张。
横向滚动（`deltaY === 0`）照旧放给浏览器，触控板横向滑仍用来浏览缩略图本身。
监听器挂在条上并 `preventDefault + stopPropagation`，不会把事件漏给查看器的页面滚动锁。

**尺寸：先整体 2 倍，再整体缩小 1.5 倍**：一枚缩略图 `--strip-dot`
（= `(space-64 + space-4) / 1.5` ≈ 45.33px，由 34px 放大到 68px 后再缩 1.5 倍得到），
外圈外扩 `space-4`，选中那张在此基础上再放大 `1.5` —— 两档是相乘的，所以选中态实测约 68px。
这个 1.5 也是 `.viewer__stripbox` 上下内边距取 `space-20` 的唯一原因：
`overflow-x: auto` 会把纵向一并算成 `auto`，内边距必须大于选中的溢出量
（约 17.3px），否则选中那一枚会被裁掉上下两边。

**圆角为什么从 `radius-full` 收到 `radius-xl`**：条高只有 80 多像素，`radius-full` 的半径会被
钳到半个条高，两端直接变成半圆 —— 选中那枚的方角外圈于是把边框顶出弧线，看起来像
「圆角在变形」。收到 `xl` 后四条边始终是直线：缩放的是照片，不是边框。

> `layoutId` 除这里的「游标」之外，还用于墙面与列表的重排补间（见 §4.4 的「重排（FLIP）」）——
> 三处都只做「同一批元素换位置」的补间，不涉及进出场，因此没有 §6.1 那类时序耦合。

### 4.4 日期读数与进度轨

进度轨已抽成两个共用件：纯展示层 [`ProgressRail.tsx`](../apps/web/src/components/ProgressRail.tsx) +
参数化行为 [`useProgressRail.ts`](../apps/web/src/hooks/useProgressRail.ts)，画廊的
**墙面与列表两个视图共用同一份轨**，各自只提供一条「读到哪个月」的读数策略
（`RailStrategy.read`），行数从两份各写一遍降到一份。

这条轨有**两个正交的维度**，都不新增代码路径，只换参数：

**① 朝向**（`RailOrientation`）—— 纵向版钉在列表左缘，横向版浮在墙面正下方居中
（`.rail-dock`：`fixed` + `left: 50%` + `translateX(-50%)`，任何屏宽都居中，
`fixed` 脱离栅格流所以不顶走照片，瀑布流底部让开 `--rail-dock-h`（98px）即可）。
两者共用同一份刻度数据，`ProgressRail` 只把「比例」映射到纵向的 `top` 或横向的 `left`。

两种朝向是**两套相反的隐喻**，这是它们唯一的实质差别：

| 朝向 | 谁不动 | 谁在动 | 进度怎么表达 |
| --- | --- | --- | --- |
| 纵向（列表） | 尺子（整条轨） | 游标（滑块 + 命中标签） | 已走过的填充自起点长到滑块 |
| 横向（墙面） | 游标（滑块 + 读数） | 尺子（时间线整体左移） | 取消填充，改用中心光带 |

**横向的「时间线移动」**由舞台（`.progress-rail__stage`）的一条 `translateX` 驱动：

```
translateX = 50cqw − 端让位 − 进度 × (舞台宽 − 2 × 端让位)
```

`50cqw` 取自 `container-type: inline-size` 的可视窗，即**视野半宽**（`100%` 在 `translateX` 里
是舞台自身宽度，与 `cqw` 不是同一把尺子，这点必须分清）。于是
**进度 0 时最新一刻正好落在正中、进度 1 时最旧一刻也落在正中**，
两端对称；「2026 年起点居中、右侧摊开后续刻度」就是它的自然初态。
过渡用 `fade('fast')` 吸收滚轮一格一格的跳变，拖拽时移除（优先保证跟手性，与滑块/填充同一条原则）。

横向的滑动点因此**必须画在可视窗之外**（滑块与 `.progress-rail__focus` 挂在轨根层，与舞台平级）：
一来它不参与平移，二来它的光晕要向上洇出停靠条 —— 留在 `overflow: hidden` 的可视窗里会被整块裁掉。
光带（横向渐隐的 accent + 向上 `box-shadow`）以 `--rail-pulse-cycle`（2600ms）缓慢呼吸：
它不属于交互动效的 150/200/300ms 三档（那三档描述「一次交互的反馈时长」），是常驻的环境光，
因此单独一个慢周期；`prefers-reduced-motion` 下关掉动画、保持常亮。

**② 粒度**（`RailScale` = `month` / `day`）—— 由工具栏的「月 / 日」胶囊切换。
实现上只把刻度键的截取长度从 `YYYY-MM` 换成 `YYYY-MM-DD`，**高亮、跳转、分组与分隔线的口径完全不变**，
因此刻度数据本身是同一套算法换参数。但**版面会整体重排**：分组边界重切、
图墙的跨刻度分隔线数量成倍变化，两者都会把照片推到新的位置 —— 这一段位移必须补间，
否则就是一次硬跳（见下面的「重排（FLIP）」）。
日尺度下刻度会翻到两三倍，横向轨的落点因此要重新整形、时间轴可能按需加长（见下一节），
纵向轨不受影响。
粒度一变，**大单位的层级跟着下沉**：月尺度下大单位是「年」，日尺度下变成「月」，
外车道与加粗刻度只看 `isMajor` 这个标记，不认具体单位。

**抽稀**：内车道文字有上限（`MAX_MINOR_LABELS`），超了按 `labelEvery` 步长抽稀。
被抽稀的标签**仍然渲染**、只是收成 `opacity: 0` —— 不摘节点，切粒度时就不会有元素进出导致的重排跳动。
抽稀只发生在纵向：横向的时间轴会按内容加长，因此逐枚都能写字。

**落点整形与按需加长（只发生在横向）**：横轨只有一屏宽，日尺度下刻度会翻到两三倍，
相邻两枚刻度的**真实几何间距**折算到舞台上可能比一个日期标签还窄，
于是会出现两个数字糊在一起的情况。因此落点先过一遍 `densifyMarks`：按时间序推着走，
理想落点与「上一枚 + 半字宽之和 + 空隙」取较大者 —— **稀疏处保持真实位置、密集处才被往后推**。
推完的总跨度超出停靠条时，舞台按这个跨度加长：**不是为了藏起来滚动，而是为了让整条时间线更长** ——
平移模型下跨度越长、同样的进度差就走得越远，密集处的数字因此有地方站。
实测日尺度 21 枚刻度把舞台从 1008px（可视窗宽）延到 1131px，可见区相邻最小间隙 31px、零重叠。

> 时间分段带来的变化：每个时间单位现在对应**一整条横带**，段的先后就是时间的先后
> （实测日尺度 22 段的最上沿逐段递增、段间最小间距 255px）—— 在此之前，
> 同一段时间分散在 N 条互不相关的纵列里，刻度位置只能靠「跨列取最小值」对齐。
> 该口径未变（见 `useGalleryRail` 的 `buildMeasuredMarks`），两视图仍然共用一把尺子。

由此**落点与跳转必须分开**：`RailMark.ratio` 是整形后的落点（画在哪），
`RailMark.progress` 是真实滚动比例（跳到哪）。跳转一律走 `progress` ——
若沿用 `ratio`，日尺度下点「4月」会跳到别的月份去。
代价要如实说清：整形过的那几枚刻度不再与滚动位置重合，
因此**读数切换的瞬间，中心游标未必正压着那一枚刻度**（实测最大偏差约 130px / 视野的 13%）。
读数本身仍然忠实（取「已越过的刻度里时间序最靠后的一枚」），
这是「数字不许互相盖住」这条底线必然要付的代价。

**读数判定不能用「遇到第一枚没越过的就停」**：那个写法把正确性押在「刻度位置单调递增」上，
日尺度下并不稳妥（纯轮转分列时期实测 4/19 在 4/26 之上；时间分段后墙面每个时间单位独占
一条横带、顺序天然正确，但这条规则不依赖排布，因此保留）。改为遍历全部、取「已越过判定线的刻度里
时间序最靠后的一枚」—— 否则点「4/26」会读到「6月6日」。

**重排（FLIP）**：切粒度的两个后果——列表的分组边界重切（照片会搬到另一行、另一个 `<ul>` 里）、
图墙的分段边界重切（一条整行分隔线增删、段内的 N 列子网格整体重建，照片跟着成段挪位）——
都不是「渐隐渐现」能表达的，用户要看的是**照片怎么挪到新位置**，
因此用 Motion 的布局投影做补间（`reorder`，取 `springs.smooth`）：

| 视图 | 挂在哪 | 为什么 |
| --- | --- | --- |
| 墙面 | `.masonry__item`（新增的一层透明外壳）上的 `layoutId={photo.id}` | 分段重切后照片常搬进**另一个段的子网格**（父节点整个换掉），普通 `layout` 认不出是同一张；外壳本身也是必需的 —— `PhotoTile` 的根节点已被指针附着 / 聚拢 / 抬起三条 MotionValue 占满，再叠布局动画会互相覆盖 |
| 列表 | `.list__cell` 上的 `layoutId={photo.id}` | 同上：分组重切后列表项的父节点整个换掉，`layoutId` 用稳定身份把新旧矩形接上 |

外壳 `.masonry__item` 对排版完全透明（无内边距、无边框，卡片自己的下边距照旧给出那条发丝缝）；
**不为它设 `display: flex`** —— 多包一层格式化上下文只会让间距的来源变得不可见。

**下面的表格描述的是纵向版（列表视图）**。横向版按上面的「两套隐喻」读：
填充一行不适用（进度改由中心光带表达），滑块与读数恒在正中不动，
剩下「刻度标签的落点与高亮」两者完全一致（横向不换边，命中只换颜色）。
为避免与具体单位耦合，下面正文里的「月份 / 年份」请按 **小单位 / 大单位**（`minor` / `major`）来读
—— 日尺度下它们分别是「日 / 月」。

| 动作 | 表现 | 参数 |
| --- | --- | --- |
| 滚动 | 已走过的进度填充**自下而上**生长，**顶端正好停在滑块上** | `fade('fast')`；拖动时 `INSTANT` |
| 滚动 | 滑块随进度上下移动 | 同上 |
| 滚动 | **月份标签换边**：到达它那个时间点时从轨左滑到轨右并点亮 accent，越过之后滑回左侧 | CSS `transform var(--motion-duration-slow)` + `var(--motion-easing-in-out)` |
| 滚动 | **年份标签只变色**：命中该年时点亮 accent，**位置一动不动**（钉死在最外侧车道） | CSS `color var(--motion-duration-base)`，无位移 |
| 滚动 | 命中态的**月份**标签纵向跟着滚动点走（贴住滑块） | `top: var(--rail-progress)`，`var(--motion-duration-fast)` + `in-out` |
| 点击月份刻度 | 跳到该月首张照片的位置（与拖动共用 `jumpTo`） | — |
| 点击年份标签 | 跳到该年第一枚刻度的位置 | — |
| 拖动 / 键盘 | 指针或方向键直接改写进度（`aria-valuenow` 同步） | 拖动中显式 `INSTANT` |

**拖拽的命中区与两种映射**：命中区——纵向落在**轨道本身**（那条 16px 的尺子），
横向落在**轨根**（整条停靠条任意位置都能按下，而不只是滚动点左右一小段）。
映射——纵向是**绝对**的（轨不动，按哪读哪，按下即跳）；横向是**相对增量**的
（时间线跟着手走：手指横向走多少像素，时间线就移多少像素）：

```
进度 = 按下时的进度 − 指针位移 / 轨道宽        （轨道宽 = 舞台宽 − 2 × 端让位）
```

分母取**轨道自己的宽**，因此指针走满一轨正好是进度 0 → 1。

**横向为什么不能用绝对映射**：横向的轨道活在会被 `translateX` 平移的**舞台里**，
拿它的矩形当坐标系，等于把指针锚在一个**随进度移动的参考系**上 —— 越拖越偏，
进度会在 0.5 处形成固定点、两侧被夹死（改前的实测症状正是「左半边固定向左、右半边固定向右」，
方向与手势无关）。相对增量的基准锚在**不动的那一层**（舞台宽、端让位都是常量几何），
因此不存在自反馈：手指右移 → 时间线右移 → 露出较早的一段 → 进度减小，
方向与手势严格同向。代价要如实说清：**横向按下不再立即跳转**（横向没有可信的绝对坐标，
按下即跳会让内容在手指下窜一下），单击跳转仍由刻度标签承担；纵向保留「按哪读哪」。

**指针捕获与点击的三条约定**（都来自同一次实测：捕获后浏览器会把随后的 `click`
改派给**捕获元素**，`click target = 捕获元素`，标签自己的 `onClick` 再也收不到）：

| 情形 | 处理 |
| --- | --- |
| 拖动超过了 `DRAG_SLOP`（4px，与 Viewer 区分点击/拖曳同一档） | 吞掉末尾那一次 `click`（`onClickCapture`）—— 否则按下落在刻度标签上时，松手后补发的 click 会**盖掉刚拖出来的进度** |
| 按下落在刻度标签上、还没拖动 | **不立刻捕获**，等越过 `DRAG_SLOP` 再补捕获 —— 否则标签的点击跳转永远收不到 click |
| 指针在窗口外松开（收不到 `pointerup`） | 用 `event.buttons === 0` 自愈，避免接下来的悬停移动一直带着时间线跑 |

**防选**：拖动期间在 `body` 上置 `user-select: none`（按下时置、松手恢复），
并且横向轨**常驻** `user-select: none`（含 `-webkit-` 前缀）——
于是拖动过程中的拖影不会把刻度文字选成一片高亮，双击刻度数字也选不中（实测真实双击后
`getSelection().rangeCount = 0`）。触控动作交集给 `touch-action: pan-y`：
横向拖拽不抢竖向滚动手势，纵向滑动仍然交给页面。

**语义不跟着命中区走**：`role="slider"` 与 `aria-*` **永远挂在轨道上**，
横向也不挪到轨根 —— `role="slider"` 的子树在无障碍树里是**装饰性内容**，
刻度标签一旦落进它内部就整批从树里消失（实测：8 枚「跳到 …」按钮全部不再暴露），
而那是可点的功能，不能只对读屏隐藏。命中区与语义因此拆成两组属性：
事件跟命中区、语义留在轨道。

**刻度标签为什么要换边**：每一枚年月刻度都带一枚标签（月份形如 `9月`，年份形如 `2026`）。
**月份**默认停在轨道**左侧**，滚动到达它那个时间点时平滑滑到轨道**右侧**并点亮 accent，
越过之后再滑回左侧 —— 「我现在在哪个月」因此不需要另做图腾，右侧那一枚就是答案，
且稳定读过整份档案。换边用纯 CSS `transform` 过渡实现：抽出 `--month-shift` 让
命中与未命中的 `translate` 两端**形状一致**（同一项百分比 + 同一项 px），
浏览器才肯逐项插值出平滑的横移。

**年份为什么不换边**：年份是这条轨的「章节」而不是「当前读数」——
它一换边，整条轨的左侧就只剩月份一层，年份这个路标会跟月份一起在轨两侧来回跳，反而更难定位。
因此年份**钉死在最外侧车道、连纵向也不动**，命中该年只把字色从 tertiary 提到 accent：
颜色是一次纯状态变化（§2 的判据：不需要逐帧数值），所以它归 CSS，用 `duration.base`；
它也因此**没有** `transform` 过渡 —— 位置恒定就不该留一段永远用不到的位移过渡。

**为什么只有月份用 `motion.easing.in-out`**：其他位移都是「一次性到位」（进场、抬起、翻页），
`easing.smooth` 那种快起慢收最合适；而月份标签是**往复**的 —— 同一个元素还会滑回原位，
两端都得慢下来，去与回才读成同一件事的两半（见《设计语言-Token规范》§3.9）。
时长用 `duration.slow`（300ms），落在规范给的 300–500ms 区间内。

**两条标签车道**：年份（15px semibold）比月份（11px medium）大一号，如果同占一条车道、
年份上抬半个行高，它会正好压住上一枚月份标签 —— 实测密集处相邻月份标签只有 14.9px 间距。
因此拆成两条车道：**年份在最外侧**（`--year-gutter: space-32`），**月份贴着轨道**。
两者都停在 `--mark-ratio`（自己那枚刻度处），年份再上抬半个行高，
所以「2026 / 8月」始终是一组上下对齐的文字，间距恒为 16px（实测 `yearCenter − monthCenter = -16`）。
月份命中后改停 `--rail-progress`（滚动点），此时它只横向滑到轨右，**纵向**跟着滑块走。

**顶部安全边**：轨道起点紧贴置顶工具栏（stuck 时轨道顶在 `TL_LINE` = 104px，上方分类 chip 占到约 107px），
轨道两端的标签会伸进 chip 那一行。因此纵向落点加下限 `clamp(var(--space-32), …, 100%)`：
标签中心不允许高过「轨道顶 + space-32」。取 32 而不是 16，是因为**两条车道共用同一条下限** ——
只有共用，年份的上抬才继续表现为「中心高 16px」，否则会被顶成同一行。
代价是进度落到最顶端时标签会略微滞后于滑块（实测：p=0 时差 32px，p>4% 后差 0），
这是刻意换取「绝不与工具栏冲突」。

**工具栏与左轨为什么要「零位移」、以及怎么做到**：`position: sticky` 只有在
「静态位置 ≠ 吸附点」时才会产生位移 —— 静态位置在吸附点之下的那段距离，会成为滚动开头
先被推着走的一小段。因此**吸附点与静态位置必须严格相等**：

| 元素 | 吸附点 | 静态位置 |
| --- | --- | --- |
| 工具栏（chip / 视图切换 / 排序胶囊） | `top: var(--size-header)` = 48 | 模块顶部留白（`.module--gallery` 收窄到 `size-header`）= 48 |
| 左轨 | `top: var(--tl-line)` = 104 | 工具栏底 = 48 + 工具栏高 56 = 104 |

于是这四件东西（时间线左轨、分类 chip、墙面/列表胶囊、倒序胶囊——后三者同处一条工具栏）
在滚动时**一动不动**地钉在视口里。`--tl-line` 因此是精确值、不能给余量：差 1px 都会先跳一下。
零位移还有一个附带好处：sticky 仍在文档流内，**占位自动保留**，内容不会被压到工具栏底下，
也就没有「固定悬浮元素遮挡内容」的问题（实测 768 / 800 / 2560 三个宽度下，
工具栏高恒为 56、未换行，`.masonry` 顶边正好落在 104）。

**为什么标签层要离开轨道元素**：整条轨道是拖拽命中区，标签若挂在轨道里就得
`pointer-events: none`，也就没法点击跳转。因此标签层（`.progress-rail__floaters`）与轨道
**并列为兄弟**：同一套 `top` 比例（两者等高），标签层整体 `pointer-events: none`、
标签自身恢复 `auto`，轨道拖拽命中区保持完整。标签 `tabIndex={-1}` —— 43 枚刻度不该占满
Tab 顺序，键盘跳转由轨道上的 ↑↓ 承担。

**读数长在哪**：月份与年份都**不再另做图腾** —— 月份命中那一枚自己滑到轨道右侧并跟着滚动点走，
它就是读数；年份则靠命中变色的那一枚回答「读的是哪一年」。两者都用 accent 字色表达选中态，
不需要材质底。

**两个视图的接入方式**：画廊只有墙面与列表两种视图（时间线式已取消），两者都走
*档案时间刻度* —— 量出每张 `[data-photo]` 节点在滚动范围里的**真实几何**
（跨列取最小值，保证月份一段落在同一处），纯测量、不做下标换算。
墙面与列表共用同一份刻度：分组、分隔线、轨上刻度因此读的是同一段时间。

**为什么读数取「刻度表」而不是「屏幕上最靠上那张」**：读数与进度必须共用一条映射
（拖到某处 → 显示某个读数，滚到某处 → 同一个读数），因此它只能来自**唯一一份**测量数据。
刻度表（每个时间单位在滚动范围里最靠上的实际像素比例）正好是这一份：读数、高亮、
点击跳转全从它出，任何视图、任何进度下都给同一个答案。
曾按「最新一张可见照片」读数：墙面早期是多列瀑布流，五列在同一时刻各有一张卡片
被判定线穿过，读数会被最高的那一列主导（滚到 45% 还报 9 月）。
现在墙面已改为按时间分段（§4.1），同屏并存的时段大幅收窄，但口径不变 ——
`read()` 仍只读刻度表，不再引入第二套公式（两套公式必然在边界上冲突：
同一屏里读数说 6 月、高亮却停在 7 月）。

> ⚠️ 因此读数回答的是「拖到档案的哪一段」，**不是**「屏幕上显示的是几月」。
> 需要严格的时间轴语义时应改布局（如已落地的按时间分段），
> 而不是改这里的读数函数 —— 请勿把 `read` 改成 DOM 式读数。

**为什么照片要先按 `filters.sort` 排序**：档案刻度的前提是「列表本身按日期有序」。
`packages/core` 的 `PHOTOS` 是「近期乱序行 + 历史升序行」拼起来的，**不是日期序**，
直接拿它索引会读出跳变的年月。故渲染前先按 `filters.sort` 排一份 `ordered`。
正序/倒序开关长在画廊置顶工具栏上，是跨视图共享的（切视图后选择仍保留）。

**刻度为什么按「年月变化处」打点**：一张照片一个刻度会挤成实心条（50+ 张时毫无信息量），
按月份打点才把「照片的时间分布」画出来 —— 密集的月份挨得近，空档一眼可见。

**填充与滑块为什么天然对齐**：两者都从同一次测量的 `progress` 算 ——
滑块写 `top: progress%`（自顶算），填充写 `height: (1 − progress)%`（自底算，
顶端因此落在 `progress` 处，正是滑块所在的高度）。写反会得到两根错开的条。

**留白列**：命中的**月份**标签从轨道向右伸出，因此网格给轨的右侧留了一条空列（见 §6.5）。
月份标签实测约 18px，这一栏取 `space-32` 即可，同时把内容区推离轨道（实测标签右缘与内容区之间
仍有 15.6px 余量）。年份不再换边，因此不必再按四位数字的宽度（约 38px）预留这一栏；
轨的**左侧**另有两条标签车道（年份 `space-64` + 空隙 `space-16`），容纳两条车道的标签。

### 4.5 模块切换 / 控件反馈

| 动作 | 实现 |
| --- | --- |
| 模块进场 | `.module` 的 `module-in`（CSS） |
| 胶囊、chip、图标按钮的 hover/active | CSS `transition` + `motion.duration.base` |
| 查看器箭头、比例标签的 hover 显隐 | CSS `transition` |

> 这三类只改 `background` / `color` / `box-shadow` / `opacity`，属于纯状态反馈，
> 留在 CSS 里更短也更好维护（见 §2）。**它们不参与 Motion，是有意为之。**

## 5. 性能约定

1. **只动 `transform` 与 `opacity`**：这两个属性不触发布局与重绘，动画期间主线程不参与绘制。
   `PhotoTile` 因此只有**一层** `motion` 元素：`article` 自己承担附着 + 抬起 + 聚拢 + 放大，
   照片长在它里面、跟着同一个变换矩阵同比放大。多一层内层缩放反而会引入两条独立弹簧，
   实测错位到 9.9px（§4.1）。
2. **hover 不进 state**：附着用 `useMotionValue` + `useSpring`，指针移动**不触发任何 React 渲染**。
   只有「谁的 hover 变了」进 state —— 因为它要影响邻位。
3. **测量要批量，且只读布局值**：聚拢几何用一次 `querySelectorAll` + 一次 `map`，
   读的是 `offsetLeft / offsetTop / offsetWidth`（布局值），**不是** `getBoundingClientRect()` ——
   后者会取到「动画跳到一半」的坐标：鼠标从一张移到旁边一张时几何一变、聚拢量跟着变，
   周围照片就会跟着指针抖。offset 读到的永远是静止位置（前提：同容器内的卡片是兄弟节点、
   共享 `offsetParent`）。一次批量读也避免了「读-写-读」交替触发强制重排。
4. **memo 到底**：`PhotoTile` 与 `ProgressiveImage` 是 `memo`（它们处在「一张卡片动、
   其余四十多张都要重渲染」的热路径上）。注意：传给 memo 组件的回调必须是稳定引用，
   否则 memo 形同虚设。
5. **不要无限循环动效**：本工程没有往复循环动画。邻位是**一次性**聚拢，由 hover 状态切换驱动；
   早先挂在第一圈邻位上的持续起伏（呼吸）已移除 —— 它既让周围照片跟着指针抖，也不提供信息量。
6. **几何量只测一次**：聚拢几何在 hover 切换时量一次；查看器安全区靠 `useViewport()`
   （只在 resize 时变）。生成几何的数据源（图片纵横比）是内联钉死的，正常滚动不触发重排。

## 6. 已知问题（结论可直接照用，无需重复验证）

### 6.1 `layoutId` + `AnimatePresence` 不适合做「网格 → 全屏」的进出场

共享元素动画与 `AnimatePresence` 组合时，**退场要等布局投影结算完才允许移除节点**。
节点残留期间若再次打开，新节点会继承「正在退场」的 presence 状态而**跳过 enter 动画** ——
实测表现为背板不透明度卡在 `0`、整层不可见，且现象随重渲染时机时好时坏。

**结论**：查看器改用确定性 FLIP（§4.2）。`layoutId` 只保留给「同一容器内的一枚游标」（§4.3）。

### 6.2 Motion 的 spring 不支持 `repeat`

`transition={{ type: 'spring', repeat: Infinity }}` 会被**静默忽略**，动画停在最后一帧 ——
实测邻位照片的缩放恒定在 0.9961，完全不振荡。

**结论**：若将来真需要循环微动，只能走 `duration` + `easing`（tween）。本工程已不需要它 ——
邻位改为一次性扩散后，`breath()` 与 `motion.duration.breath` token 一并删除（本条留作反例）。
判断规则：**一次性空间运动 → spring；非空间状态 → tween。**

### 6.3 StrictMode 双挂载会吃掉「挂载期动画」

开发期 `React.StrictMode` 会挂载 → 卸载 → 再挂载。Motion 的 `initial → animate`
（挂载时才播的那次）在第二次挂载时可能被跳过 —— 实测画框停在起点不动、背板恒为 0，
要等下一次重渲染才补上，表现为「时好时坏」。

**结论**：需要进出场的组件（查看器）不要依赖挂载期动画，改用
`initial={false}` + **状态变化**驱动：初值就是起点，挂载后下一帧用
`requestAnimationFrame` 把目标交出去，Motion 就会看到一次真正的 `animate` 变化。
两种模式下都确定。

### 6.4 `scrollbar-width` / `scrollbar-color` 会让 `::-webkit-scrollbar` 整套失效

Chrome 一旦在某个元素上看到标准属性 `scrollbar-width` **或** `scrollbar-color` 的非 `auto` 值，
就**弃用**该元素上的 `::-webkit-scrollbar` 系列伪元素。
实测：写了两者之后滚动条宽度退回 10px，`::-webkit-scrollbar-button { display: none }` 也未必生效。

**结论**：Chrome 侧只写 `::-webkit-scrollbar`（8px + 胶囊滑块）；
Firefox 侧用 `@supports not selector(::-webkit-scrollbar)` 单独给标准属性。
两端产物分别是「8px / 主色 40% 半透明」与「`thin` / 同一个主色」。

**查看器打开时怎么「隐藏」滚动条**：不摘滚动条、也不改 `overflow` —— 两者都会让视口宽度变化
（实测 15px），页头与左轨会跟着重排，而重排发生在查看器的半透明背板底下，读起来就是
「一开一关，背后闪一下」。改成**只把滑块画成透明**（零重排），滚动本身由 Viewer 拦掉的
滚轮 / 触摸 / 按键输入负责。
⚠️ 这条「变透明」也必须关进 `@supports not selector(::-webkit-scrollbar)`：
它写的是 `scrollbar-color: transparent transparent` —— 仍是「非 auto 值」，在 Chrome 里
会把上面的伪元素规则再踢掉一次，宽度从 8px 退回 15px（实测 `clientWidth` 2552 → 2545），
等于绕一圈又把重排引了回来。

### 6.5 留白列必须显式指定列号

进度轨给「命中后向右伸出的月份标签」留了一条空列（第 2 栏），但网格的自动排布会把内容区排到那条空列上
（DOM 顺序是：轨、内容 → 依次落到第 1、2 栏）。
**结论**：只要网格里存在「故意空着」的列，其余子项就必须写 `grid-column` 锁定列号；
窄屏改成单栏时还要记得复位成 `auto`。
该取舍的代价随列宽上升：这一栏是为**最宽的那枚标签**留的，若留得太窄，标签会压进内容区
（实测早期版本：年份标签压进内容区 23px，`yearRightGapToMasonry: -23.3`）——
而标签层 `z-index` 高于内容，于是它会盖在照片上。
现在是「月份 18px + 一格呼吸 = space-32」，实测余量 15.6px。

## 8. 新增一个动效的检查清单

1. **判断归属**：逐帧数值 + 时序控制 → Motion；纯绘制类状态 → CSS（§2）。
2. **取参数**：能从 `lib/motion.ts` 拿到就不写新数字；拿不到就先加 token（§3）。
3. **判断类型**：一次性空间运动 → `spring`；非空间状态 → `fade()`；**不做无限循环**（§5 第 5 条）。
4. **检查渲染成本**：是否只动 `transform`/`opacity`？指针类输入是否走了 `MotionValue`？
   传给 `memo` 组件的回调是否稳定？
5. **想清楚进出场**：需要退场的组件不要依赖挂载期动画（§6.3）。
6. **无障碍**：确认 `MotionConfig reducedMotion="user"` 仍然覆盖得到（不要给动画加
   `display: none` 之类会绕过它的开关）。
7. **补文档**：把这条动效加进 §4 的清单。
